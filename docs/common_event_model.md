# Common Event Model

## 1. What is the Common Event Model?

The **Common Event Model** is a standardized data structure designed to represent all security-relevant events generated by different monitoring components (processes, system resources, command line analysis, file system activity) in a uniform, structured format.

Instead of each monitor producing custom, unstructured dictionary formats or text messages, every event is transformed into a standard `Event` object containing common metadata (ID, timestamp, source, event type, severity) and module-specific details.

---

## 2. Why is it Needed?

Before the Common Event Model was implemented, each monitoring subsystem produced distinct data formats:
* `process_monitor.py` returned raw dictionaries with keys like `pid`, `name`, `cmdline`.
* `resource_monitor.py` returned complex nested dictionaries containing CPU and memory states.
* `file_monitor.py` printed strings directly from Watchdog file system event objects.
* `risk_detector.py` produced risk dictionary output with `score`, `level`, and `reasons`.

This data fragmentation created several problems:
1. **Inconsistent Logging**: Log messages were formatted differently depending on which component generated them.
2. **Difficult Correlation**: Future features like Event Correlation and Composite Risk Engine require comparing events across process, file, and resource monitors. Without a common data schema, cross-component event matching would require custom conversion logic for every pair of monitors.
3. **Lack of Serialization Standard**: Exporting events for external analysis or UI display required ad-hoc formatting.

The Common Event Model solves this by acting as a single, normalized schema across the entire application.

---

## 3. How it is Implemented

The model is implemented using Python's standard library `@dataclass` in [src/models/event.py](file:///c:/Users/ACER/projects/endpoint-monitor/src/models/event.py).

* **Dataclass Schema**: `Event` defines standard attributes (`event_id`, `timestamp`, `event_type`, `source`, `severity`) along with optional context blocks for process, file, resource, and detection details.
* **Default Values & Optional Fields**: Context fields default to `None` or empty lists/dicts so that an event from one module (e.g., file monitoring) does not need to supply process or resource information.
* **Factory Helper**: `Event.from_process_info()` provides a clean class method to instantiate events directly from process dictionary snapshots.
* **Serialization**: `Event.to_dict()` converts event instances into standard Python dictionaries suitable for JSON serialization or logging.

## 5. Event Structure

| Field | Type | Required/Optional | Purpose |
| :--- | :--- | :--- | :--- |
| `event_id` | `str` | **Required** | Unique UUID v4 string for tracking and correlation. |
| `timestamp` | `float` | **Required** | Epoch timestamp when the event was generated. |
| `event_type` | `str` | **Required** | Category (`process_start`, `resource_anomaly`, `file_action`). |
| `source` | `str` | **Required** | Originating module (`process_monitor`, `resource_monitor`, `file_monitor`). |
| `severity` | `str` | **Required** | Standardized severity level (`LOW`, `MEDIUM`, `HIGH`). |
| `pid` | `Optional[int]` | Optional | Process ID for process events. |
| `ppid` | `Optional[int]` | Optional | Parent Process ID for process events. |
| `process_name` | `Optional[str]` | Optional | Name of the process executable. |
| `parent_process_name` | `Optional[str]` | Optional | Name of the parent process executable. |
| `username` | `Optional[str]` | Optional | User account owning the process. |
| `command_line` | `Optional[List[str]]` | Optional | Command line arguments list. |
| `file_path` | `Optional[str]` | Optional | Path of the file involved in a file event. |
| `file_action` | `Optional[str]` | Optional | File action (`created`, `modified`, `deleted`, `moved`). |
| `dest_path` | `Optional[str]` | Optional | Destination path for file move operations. |
| `resource_metrics` | `Optional[Dict[str, Any]]` | Optional | Usage metrics dict for resource anomaly events. |
| `network_info` | `Optional[Dict[str, Any]]` | Optional | Reserved for future network monitoring telemetry. |
| `indicators` | `List[str]` | Optional | Detected security indicator tags (`encoded_command`, etc.). |
| `risk_score` | `int` | Optional | Calculated risk score. |
| `risk_level` | `str` | Optional | Evaluated risk severity level (`LOW`, `MEDIUM`, `HIGH`). |
| `risk_reasons` | `List[str]` | Optional | Human-readable explanation of risk points assigned. |
| `metadata` | `Dict[str, Any]` | Optional | Extensible metadata key-value mapping. |

## 6. Functions and Classes

### `Event` (`src/models/event.py`)
* **What it does**: `@dataclass` representing a single, standardized security event.
* **Input**: Attribute parameters (or default initializations).
* **Output**: Instantiated `Event` object.
* **Why it is used**: Acts as the central data contract for all security events.

### `Event.to_dict()` (`src/models/event.py`)
* **What it does**: Converts an `Event` instance into a standard Python dictionary using `dataclasses.asdict`.
* **Input**: `self` (`Event` instance).
* **Output**: `Dict[str, Any]`.
* **Why it is used**: Enables easy JSON serialization, logging, and inspection.

### `Event.from_process_info()` (`src/models/event.py`)
* **What it does**: Class method that maps raw `process_info` dictionaries from `process_monitor.py` into a pre-populated `Event` instance.
* **Input**: `process_info: Dict[str, Any]`.
* **Output**: `Event` instance with `event_type="process_start"` and `source="process_monitor"`.
* **Why it is used**: Simplifies event construction from process telemetry.

### `process_event_from_dict()` (`src/main.py`)
* **What it does**: Converts a process info dictionary to an `Event`, invokes `detect_command_indicators` and `calculate_risk`, and updates event risk properties.
* **Input**: `process_info: Dict[str, Any]`.
* **Output**: Fully populated `Event` instance.
* **Why it is used**: Integrates process discovery, indicator detection, and risk scoring into a single pipeline step.

### `report_suspicious_event()` (`src/main.py`)
* **What it does**: Formats and prints a suspicious process alert to console and writes warnings to `logger`.
* **Input**: `event: Event`, `logger: logging.Logger`.
* **Output**: `None`.
* **Why it is used**: Encapsulates console reporting and logging for flagged events.

### `FileMonitor.create_event()` (`src/monitors/file_monitor.py`)
* **What it does**: Helper method on `FileMonitor` to build a standardized file action `Event` from Watchdog file system events.
* **Input**: `action: str`, `src_path: str`, `dest_path: Optional[str]`, `severity: str`.
* **Output**: `Event` instance with `event_type="file_action"` and `source="file_monitor"`.
* **Why it is used**: Standardizes file event creation across Watchdog callbacks (`on_created`, `on_modified`, `on_deleted`, `on_moved`).

## 7. Event Creation Flow

```text
get_running_processes() / get_new_processes()
        ↓
raw process_info dictionary
        ↓
Event.from_process_info(process_info)
        ↓
standardized Event object (event_type="process_start", source="process_monitor")
        ↓
detect_command_indicators(event.command_line)
        ↓
calculate_risk(event.indicators, process_info)
        ↓
update Event fields (indicators, risk_score, risk_level, risk_reasons, severity)
        ↓
report_suspicious_event(event, logger)
        ↓
console alert output / logger.warning() in logs/security.log
```

## 9. Python Concepts Used

* **Dataclasses (`@dataclass`)**: Reduces boilerplate code by automatically generating `__init__`, `__repr__`, and field definitions.
* **Type Hints (`typing.Optional`, `List`, `Dict`, `Any`)**: Clarifies argument and attribute data types for maintainability and IDE auto-completion.
* **Optional Values (`Optional[...] = None`)**: Allows fields not applicable to specific event types to default safely to `None`.
* **Serialization (`dataclasses.asdict`)**: Dynamically converts dataclass instances into Python dictionaries for export and logging.
* **Class Methods (`@classmethod`)**: Used for `from_process_info` factory logic to encapsulate object creation from process telemetry dicts.
* **Default Factories (`field(default_factory=...)`)**: Generates unique values (UUID, timestamp) or fresh mutable collections (`list`, `dict`) per instance safely.

---

## 10. Why Each Major Function Exists

* **`Event` Dataclass**: Establishes a formal, typed schema for security data across the application.
* **`to_dict()`**: Provides standard dictionary conversion for logging, serializing to JSON, or passing events over network sockets.
* **`from_process_info()`**: Simplifies converting raw `psutil` process info dictionaries into `Event` objects without repeating field mappings in multiple places.
* **`process_event_from_dict()`**: Combines event creation, indicator scanning, and risk evaluation into a single modular helper function in `main.py`.
* **`report_suspicious_event()`**: Isolates console formatting and security logging logic, keeping main scan loops clean.
* **`FileMonitor.create_event()`**: Centralizes event instantiation for file system events in `file_monitor.py`.

---

## 11. Limitations

* **No Persistent Storage**: Events are currently processed in-memory and written to log files; they are not saved to a relational or document database.
* **No Stateful Event Correlation**: The model provides the data structure, but events are evaluated individually rather than across temporal windows.
* **No Network Capture Yet**: Network fields exist in the model but are not yet populated because Network Monitoring is not implemented.

---

## 12. Future Features Supported

1. **Behavioral Baseline**: `Event` fields `username`, `process_name`, `command_line`, and `timestamp` provide the standardized dataset needed to build user and process execution baselines.
2. **Process-Tree Analysis**: `pid` and `ppid` attributes enable building parent-child process tree graphs from streams of `process_start` events.
3. **Network Monitoring**: `network_info` optional field allows seamless integration of network socket and IP telemetry without schema changes.
4. **Event Correlation**: Standardized `event_id`, `timestamp`, `pid`, and `file_path` fields allow cross-event correlation rules (e.g., process launch followed by file modification followed by outbound network connection).
5. **Composite Risk Engine**: Standardized `risk_score` and `severity` fields allow aggregating risk across multiple correlated events.

## 13. Viva Questions & Answers

1. **Q: What is the primary purpose of the Common Event Model?**
   *A: It standardizes security telemetry from process, resource, and file monitors into a single, uniform data structure (`Event`), enabling consistent logging, analysis, and future event correlation.*

2. **Q: Why did you use Python's `@dataclass` for the `Event` model?**
   *A: `@dataclass` provides clean syntax, automatic method generation (`__init__`, `__repr__`), strong readability, and built-in dictionary serialization via `asdict()` without introducing third-party dependencies.*

3. **Q: How does the event model handle fields that are not applicable to every event type?**
   *A: Fields specific to certain monitors (e.g., `file_path` or `resource_metrics`) are marked as `Optional` and default to `None` or empty containers, making the class safe for all event categories.*

4. **Q: How is an `Event` serialized for logging or JSON export?**
   *A: By calling `event.to_dict()`, which utilizes `dataclasses.asdict(self)` to convert the dataclass instance into a standard Python dictionary.*

5. **Q: Why is `default_factory` used for fields like `event_id` and `indicators`?**
   *A: In Python dataclasses, mutable defaults (like lists or dicts) or dynamic values (like UUIDs and timestamps) must use `default_factory` to ensure each instance gets its own fresh object rather than sharing a single default value across instances.*

6. **Q: What problem was fixed in `file_monitor.py` during event model integration?**
   *A: An un-guarded `while True: time.sleep(1)` loop at module level was moved inside an `if __name__ == "__main__":` block so that importing `FileMonitor` no longer blocks execution.*

7. **Q: How are process monitor dictionaries mapped into `Event` objects?**
   *A: Using the `Event.from_process_info(process_info)` class method, which extracts `pid`, `ppid`, `name`, `parent_name`, `username`, and `cmdline` into event attributes.*

8. **Q: Does the Common Event Model change how command detection or risk scoring work?**
   *A: No. It preserves existing detection and scoring logic in `command_detector.py` and `risk_detector.py`, updating the `Event` object's `indicators`, `risk_score`, and `risk_level` attributes with the results.*

9. **Q: What performance overhead does the `Event` class add?**
   *A: Negligible overhead. Instantiating a standard dataclass takes fractions of a microsecond in Python, making it suitable for continuous real-time monitoring.*

10. **Q: How will this event model facilitate future features like Event Correlation?**
    *A: It provides uniform metadata (`event_id`, `timestamp`, `pid`, `ppid`, `file_path`, `severity`) across all event types, allowing a correlation engine to compare and link events from different monitors seamlessly.*
